# Design the Scenario

Choose the visible action that makes the engineering mismatch funny. Then select a composition and illustration treatment.
Use the existing [editorial design system](../../style-ref-editorial/references/design-system.md) for the default brand vocabulary.

## Match the mechanism to the composition

| When the joke depends on… | Use… | Make the viewer notice… |
|---|---|---|
| A system's unexpected response | One scene with two short dialogue beats | The final reply after the confident setup |
| Repeating an ineffective action | A short visual loop or accumulating stack | Inputs stay unchanged while effort grows |
| An execution mismatch | An expectation/actual split with matching objects | The changed label and unchanged bottleneck |
| A failure appearing after a confident claim | An illustrated completion message and a contrasting test result | The evidence undercutting the claim |
| Hidden state | A cutaway showing the cache or internal boundary | Why the old output survives the new deployment |
| Accumulated delivery | An input/output timeline or holding container | Gradual work becoming one delayed output |
| A final category breaking an established pattern | A compact comparison grid | Familiar early cells followed by one exaggerated final cell |

These are options, not mandatory templates. Do not put a joke into a grid merely because the supplied reference used one.
If a queue is the joke, draw a queue. If timing is the joke, show timing.

## Preserve a recognisable visual voice

- Start with warm paper, bold ink text, pastel groupings, and restrained blue annotations.
- Use the component's actual name where it helps recognition: retry loop, proxy, cache, event loop, or pytest.
- Use expressive poses or faces only when they add information. An unchanged response can be funnier than an elaborate character.
- Keep one focal action and a clear reading order. Give the punchline space.
- Retain quiet Madhan Kumar authorship. Do not reuse another creator's identity, artwork, or exact composition.

## Choose the rendering method

| Visual need | Preferred method |
|---|---|
| Exact code, HTTP status, test result, timeline, or diagram | SVG or HTML/CSS with deterministic labels |
| Original characters, gestures, expressions, or surreal scene | Image generation, with exact labels composed separately where necessary |
| A real failure whose actual output is the joke | Approved, sanitised capture of that actual output |
| A supplied image that the user wants edited | The available image editing workflow |

An illustrated message panel must not masquerade as a real execution trace or product screenshot.
Do not add fabricated timestamps, failure totals, or performance figures to make a fictional scene look authentic.

## Format and copy

- Default to one 4:5 image when the entire joke fits. A two-panel or four-panel image does not require a carousel.
- Use multiple pages only when the reveal needs that sequence. Stop after the punchline or brief useful consequence.
- Keep most labels to one or two short lines. Avoid paragraphs inside speech bubbles.
- At 1080 px canvas width, start near 34–42 px for key labels. Verify at roughly 360 px feed width.
- Let the caption add context or a relevant engineering observation. Do not restate every label or explain the humour.
- Write alt text that preserves the setup, contrast, and final visual beat. Avoid only saying “funny developer meme.”

## Compact asset brief

Describe the scene, actors or components, visible action, exact text, reading order, punchline placement, and chosen format.
Include the technical condition that keeps the premise true. Keep that condition in a short post note unless the image needs it.
State whether the asset is an illustration, a genuine capture, or a measured result.
Leave decorative choices open where they do not affect the joke, technical accuracy, or personal style.
